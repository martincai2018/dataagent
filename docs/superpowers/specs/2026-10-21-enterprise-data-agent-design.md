# 企业级 Data Agent 设计文档

日期：2026-10-21
状态：待评审

## 1. 背景与目标

构建企业内部使用的全场景 Data Agent，终态覆盖：

- **Chat BI**：业务用户自然语言问数，自动生成 SQL、返回图表与结论
- **数据开发助手**：SQL/ETL 生成与解释、MR 自动评审、报错诊断
- **监控运维**：调度失败诊断、IM 告警、审批后重跑
- **治理（副产品）**：问数纠错沉淀口径、Review 沉淀规范，不做独立治理平台

### 约束条件

| 项 | 现状 |
|---|---|
| 定位 | 企业内部平台（非对外产品） |
| 首发场景 | 智能问数（Chat BI） |
| 数仓现状 | 有 ODS/DWD/DWS/ADS 分层，但指标口径散落在报表 SQL、代码和分析师经验中，无统一语义层 |
| 模型 | 可使用国产商用 API（DeepSeek、通义千问等，OpenAI 兼容接口） |
| 团队 | 1-2 人，1-2 个月内出可用原型 |
| 查询引擎 | 未最终确定，需支持多引擎（MySQL/PG、ClickHouse/Doris/StarRocks、Hive/Trino 等） |

### 核心设计哲学

1. **终态按平台设计，按场景切片交付**——先定共享底座，每个场景只是同一编排内核换工具集，避免烟囱式建设
2. **框架可以换，资产不能绑死**——以 DB-GPT 为底座但核心零修改，指标口径、工具能力、评测集全部是框架之外的独立资产
3. **确定性归平台，语义理解归模型**——权限、SQL 限制、指标口径由代码和配置强制；生成类任务才交给 LLM
4. **准确率是运营出来的**——评测集 + 每周错题归因循环，比模型选型和提示词技巧更决定成败

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐

│ DB-GPT 内核（v0.8.x，版本锁定，不改核心代码）                       │

```

### 三个关键架构决定

1. **指标语义服务独立存在，不放进 DB-GPT 知识库**。知识库是模糊检索，指标口径必须精确命中（"GMV 含不含退款"不能靠相似度召回）。指标定义用 Git YAML 管理；历史 SQL、SOP 等模糊知识才走 RAG。
2. **查询网关是唯一能碰数据库的出口**。Agent 生成的 SQL 不直连引擎，必须经过网关做方言校验、只读限制、行列权限注入、行数限制、审计。
3. **调度/元数据适配各自独立成服务**。将来换调度系统、甚至换掉 DB-GPT，场景资产不受影响。

## 3. 关键组件设计

### 3.1 指标语义服务

一个指标一条 YAML，Git 管理，PR 审批即口径变更，口径有版本、有责任人、有审计。

```yaml
# metrics/gmv.yaml
name: gmv
display_name: 成交金额
aliases: [GMV, 成交额, 交易额, 销售额]
owner: data-team@xxx
formula: "SUM(order_pay_amt)"          # 精确口径，冻结
table: dws_trade_order_di
time_column: pay_time
dimensions: [channel, city, category]
filters:
  - "order_status IN ('paid','closed')"
row_filter: "city_id IN ${user.allowed_cities}"   # 权限模板
few_shot:                               # 评测错题沉淀到这里
  - q: "昨天各渠道成交额"
    sql: "SELECT channel, SUM(order_pay_amt) FROM dws_trade_order_di WHERE dt = '${yesterday}' GROUP BY channel"
status: approved                        # draft/approved/deprecated
```

接口（刻意做薄，四个）：

- `search_metric(自然语言)`：别名 + 向量混合召回，返回候选指标
- `get_metric(name)`：精确取口径
- `list_dimensions(metric)`：取可用维度
- `record_feedback(...)`：问数纠错回流

技术栈：FastAPI + Postgres + pgvector。

**冷启动**：扫描存量报表 SQL 与调度任务，LLM 批量抽取"SQL → 候选指标草稿"，人工 Web 审核入库。30-50 个试点指标允许纯手工两周录完，不在冷启动自动化上过度投入。

### 3.2 查询网关

SQL 进入后顺序过五道关，任一不过即拒绝，并把原因**结构化返回给 Agent 触发自我纠错**：

```
SQL → ①SQL 解析（只允许 SELECT/WITH，禁多语句/DDL/DML）
    → ②方言校验与 SQL 重写（限 LIMIT、强制分区裁剪条件）
    → ③行列权限注入（指标 row_filter 模板 + SSO 用户身份渲染）
    → ④审计与限流（按人/按库记录全量 SQL；大查询走队列或先 EXPLAIN 估价）
    → ⑤执行（只读账号；多引擎方言适配器：MySQL/CK/Doris/Trino）
```

- 返回结构化错误：`{stage, reason, suggestion}`，Agent 带建议重新生成，最多重试 2 次
- 高成本查询先返回"预计扫描 X 亿行，是否继续 / 是否改用汇总表"
- 多引擎支持仅体现为网关内部的方言适配器，上层无感

### 3.3 Agent 编排（DB-GPT 侧）

- 每个场景一条独立 AWEL DAG，通过自写 Operator/Tool 调用能力服务层；不修改 DB-GPT 核心代码
- **Chat BI 流**：意图识别 → 指标精确匹配（调用语义服务）→ Schema linking → SQL 生成 → 网关校验执行 → 图表/结论生成；多轮追问复用上下文
- **开发流**：SQL 生成/解释 → 沙箱 EXPLAIN/小数据试跑；SQL Review Bot 监听代码平台 MR 评论；日志诊断 tool 拉取调度日志
- **运维流**：调度 webhook 触发 → 拉实例日志 + 血缘 + 上游状态 → 诊断 → IM 卡片推送 → 审批回调 → 调用调度服务执行重跑

### 3.4 模型路由

| 任务类型 | 模型 |
|---|---|
| 复杂 SQL 生成、日志根因诊断 | DeepSeek-R1（强推理） |
| 指标匹配、问题改写、意图识别、闲聊 | Qwen-Turbo 等低成本模型 |

### 3.5 评测体系

- **黄金集**：阶段 0 收集 50 个真实业务问数原话（含对应指标、标准 SQL/期望结果特征），每周从灰度反馈补 10-20 题，阶段 3 达到 200 题
- **三层自动判定**：①SQL 可执行；②执行结果集与标准结果做顺序无关的集合比对；③图表类型/维度正确性由规则或小模型判定
- **回归**：改提示词、few-shot、换模型、升级 DB-GPT 均全量自动回归；准确率下降超过 3% 阻断发布；CI 保留准确率趋势
- 错题唯一三个出口：补指标定义/同义词、沉淀 few-shot、修系统 bug。**禁止把答案写死进 prompt 凑分**

### 3.6 安全、错误处理、可观测

- **权限三原则**：模型永不直接持有数据库凭证；所有写操作（重跑、置成功）走审批卡片并校验审批人身份；审计日志独立库、只追加
- **失败兜底链**：工具失败 → 结构化错误自纠（≤2 次）→ 降级（推荐最相近的已有报表）→ 明示不会并转人工群。**永远不编造数字**
- **可观测**：Langfuse 记录每轮规划、工具调用、token、延迟
- UI 中 SQL、取数过程、口径来源全部可见，可点"纠错"

## 4. 场景范围（一期）

| 场景 | 做 | 不做（YAGNI） |
|---|---|---|
| Chat BI | 1 个试点域（20-50 张表、30-50 核心指标）；问数→SQL→图表→结论；多轮追问；过程可看可纠错 | 自动建模、全公司域、自然语言建仪表盘 |
| 数据开发 | SQL 生成与解释、MR SQL Review 机器人、报错日志诊断、沙箱试跑 | 自动生成整条 ETL 管道、自动调优生产任务 |
| 监控运维 | 失败自动诊断、IM 推送、卡片审批重跑、血缘展示 | 自动自愈、容量预测、成本优化 |
| 治理 | 前三场景的副产品：纠错沉淀口径、Review 沉淀规范 | 独立治理平台 |

## 5. 里程碑（2 人约 14-16 周；1 人节奏翻倍）

### 阶段 0 · 骨架验证（第 1-2 周）

- DB-GPT v0.8.x Docker 部署锁版本；接通 DeepSeek；接 1 个只读测试库
- 两个最朴素的 tool：`get_table_meta`、`run_readonly_sql`（经最简查询网关）
- 交付物：DB-GPT Web 中端到端跑通"查表字段 / 昨天多少单"
- 并行：向运营/分析师收集 50 个真实问数原话

### 阶段 1 · Chat BI 打穿（第 3-7 周）

- 第 3-4 周：指标语义服务上线，试点域 30-50 指标录入；网关补齐行列权限、审计、限流
- 第 5 周：DB-GPT 问数 DAG 搭建并接入语义服务
- 第 6 周：评测闭环，50 题自动回归，目标执行准确率 ≥80%
- 第 7 周：灰度 5-10 个业务用户；第一周即拉业务/分析师进口径评审群
- 交付物：试点域真实日活的问数助手

### 阶段 2 · 开发助手（第 8-11 周）

- 沙箱执行服务（容器隔离，EXPLAIN/小数据试跑）
- SQL Review Bot 接代码平台 MR；日志诊断 tool
- 交付物：数据开发组 MR 全部经过 Bot 评审；贴日志即得诊断

### 阶段 3 · 运维闭环（第 12-16 周）

- 调度适配服务：先只读（状态/日志/血缘），后写操作（重跑/置成功，全部审批）
- 飞书/钉钉 Bot：失败告警卡片 → 诊断 → 一键审批重跑
- 元数据对接 OpenMetadata（或直连 information_schema 过渡）
- 交付物：试点调度项目失败在 IM 内完成"看诊断 → 批准重跑"

阶段 2、3 只在能力服务层加服务、在 DB-GPT 加 tool 和 DAG，不改动阶段 0-1 的架构。

## 6. 测试策略

| 层 | 测什么 | 怎么测 |
|---|---|---|
| 能力服务单元测试 | 网关五关、权限模板渲染、方言重写、语义召回 | pytest；维护恶意/越权 SQL 用例库（DROP、UNION 绕过、多语句、跨库探测等） |
| 契约测试 | 各 tool 入参/出参 schema | 固定 JSON 快照，演进不得破坏契约 |
| Agent 端到端 | 黄金评测集 | 三层自动判定 + CI 回归，跌 3% 阻断 |
| 沙箱与审批 | 写操作、资源隔离 | 定期脚本演练：审批链路、越权拒绝、大查询拦截 |
| 灰度 | 真实用户效果 | 5-10 人内测，每个回答带👍👎，👎必进下周错题分析 |

原则：**确定性逻辑（权限、SQL 限制、口径渲染）100% 靠代码测试，不靠"模型守规矩"；生成质量靠评测集。**

## 7. 团队分工与运转

- **平台向 1 人**：DB-GPT 编排、查询网关、语义服务、评测 CI
- **场景与数据向 1 人**：指标口径挖掘与评审组织、提示词/few-shot 运营、对接业务方与调度/元数据系统
- 每周节奏：周一发版（先跑全量评测）→ 周中收集👎 → 周五错题归因会，每题归入三类之一（口径缺失 / 提示词-few-shot / 系统 bug）并分别修复
- 前 3 个月设人工兜底群

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 业务方不配合录口径 | 冷启动自动抽草稿降低其成本；试点域选痛点强、协作好的业务方 |
| DB-GPT 深定制后升级困难 | 核心零修改、插件化、能力全在外部服务；版本锁定，每季度评估跟随 |
| 80% 准确率被判定"不能用" | SQL/过程/口径全可见可纠错；定位为"可信取数助理"而非永不出错的问答机；人工兜底群 |
| 查询引擎未定/多引擎 | 统一走查询网关方言适配器，上层 Agent 与指标定义与引擎无关 |

## 9. 明确不做（一期）

- 自动 ETL 管道生成、生产任务自动调优
- 任务自动自愈（所有写操作必须人工审批）
- 独立数据治理平台、自动建模、自然语言建仪表盘
- 自研 Agent 框架、自研元数据/血缘平台
